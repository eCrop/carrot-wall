Guide 1 · Day 1 · Monday 21 September

Foundations

The Carrot Wall project · the 2-hour block, at your pace

By the end of this guide the Carrot Wall runs on your machine, you have interrogated it like a colleague who knows the codebase, and your fork carries a harness you can defend: a CLAUDE.md of your own checked against the one that built the wall, the shipped hooks read and bounced, two tested guards installed, your first rule file, and a settings file that decides what never needs asking. Steps 1–3 are the morning's core; everything after is the same movement repeated on the remaining surfaces — go exactly as far as the block allows.

Start hereBefore you start

You need three things installed. Check them in a terminal:

java -version     # 21 or newer
node -v           # 20 or newer
claude --version  # any recent version; run `claude update` if in doubt

You also need the teaching harness from this morning — one worked example of each kind of thing on the tour. It sits in the repo you are about to clone, under setup-docs/teaching-harness/, so it arrives with Step 1.

If Java or Node are missing, grab them now and wave me over if the install fights you. One more thing from this morning: make sure you are signed into the company workspace, not a personal account. Real code only travels on the right accounts.

Step 0A clean view, without touching your setup

Optional, and worth it if you have used Claude Code for a while. Your existing commands, skills, plugins and memory will shape everything you see today, and the mechanism is easier to learn when nothing is doing invisible work on your behalf.

Do not delete or move your own setup to get there. That accumulated ~/.claude is your harness — the thing this whole week argues you should have. Claude Code will happily run a second, separate profile beside it, and everything below leaves yours exactly where it is.

Look at what you have first. Half the value of today is comparing it with what you build:

ls -la ~/.claude 2>/dev/null
ls -la ~/.claude.json 2>/dev/null

Then point this one terminal at a fresh profile for the workshop:

this terminal only · your ~/.claude is untouched
export CLAUDE_CONFIG_DIR=~/.claude-workshop
claude

While that variable is set, Claude Code keeps its settings, sign-in, plugins, session history and memory under that folder instead of ~/.claude. Any terminal without it is your normal setup, unchanged. And there is nothing to restore afterwards: close the terminal or unset CLAUDE_CONFIG_DIR and you are back on your own harness; the workshop profile sits in one folder you can keep for the week or throw away when it is over.

The fresh profile starts signed out

Run /login once inside it and pick the company workspace — not a personal account.

One thing the fresh profile deliberately does not blank out: the project level. The Wall you are about to clone ships with the CLAUDE.md and the .claude/ folder that were used to build it — reading and extending those files is half of today. /status shows exactly which sources are in play at any moment. And in your own repos later, the same respect applies: leave any committed .claude/ where it is. That is your team's harness, not clutter.

Then confirm the install is healthy before you start:

claude update        # it ships almost daily
claude --version
claude               # then, inside the session:
/doctor              # checks install, config, MCP servers, hooks

Step 1Fork it, clone it, run it

Open the repo at github.com/eCrop/carrot-wall and click Fork, top right. That gives you your own full copy under your own GitHub account. You will work there all week, and nothing you do can affect anyone else's copy.

Then clone your fork (the URL with your username in it):

git clone https://github.com/<your-username>/carrot-wall.git
cd carrot-wall

Two apps, two terminals:

terminal 1 · the API
cd apps/api
./mvnw quarkus:dev
terminal 2 · the web app
cd apps/web
npm install
npm start

Open http://localhost:4200. You should see the wall with a few seeded posts. If you see it, you are done with setup. If you do not, the two usual suspects are a busy port and a Node version below 20. Fix or flag.

Now create a branch to work on. Everything you do this week goes here, on your own fork:

git checkout -b day1-setup
git push -u origin day1-setup

At the end of each day, open a pull request from your branch back to the original repo. GitHub offers it automatically after you push: the Compare & pull request button, with the base repository set to the original and the base branch master. Nothing gets merged; the pull request is simply where I read your work and leave comments between sessions. You will do this for the first time at the end of today.

Step 2Interrogate the codebase

This is the exercise. You just cloned a project you have never seen. Instead of reading files for an hour, ask.

Start Claude Code at the repo root:

cd ../..   # back to the repo root
claude

Then ask it the kind of questions you would ask the senior developer who wrote this. Ask at least five. Some to steal, but yours will be better because you are curious about different things:

  • How does a post get from the submit form to the wall? Walk me through every file involved.
  • Where is the rate limit enforced, and what exactly happens when someone hits it?
  • What would I need to touch to add a new post type? List the files.
  • Explain the Flyway migrations in this repo. What does each one set up?
  • Why does the wall update without a page reload? Show me the mechanism.
  • What is the ugliest part of this codebase, and why?

Two habits to practice while you do this:

Check the citations

A good answer names real files and real lines. When it does, open one and confirm. When an answer feels confident but cites nothing, be suspicious. You are calibrating your trust, and that calibration is the actual skill here.

Watch your context

Run /context once mid-session and look at what is taking up space. We will talk a lot more about this on Wednesday, but it is good to see the numbers early.

Goal

Three answers that cite real files and survive your checking.

Step 3Write your own CLAUDE.md — against ours

CLAUDE.md is the file Claude Code reads at the start of every session in this project. The repo already has one: it was written by /init while the wall was being built — the exact moment you saw in this morning's recording — and then hand-tuned. That changes the exercise, for the better: you get to write yours and then check it against a real one.

First, read ours actively. Open CLAUDE.md and pick two claims to verify yourself — run the command, open the file it names. Two good candidates: "no eslint / npm run lint in this repo" and the rule about never mutating a Post through a bulk update(...). A memory file earns trust one verified line at a time.

Then move it aside and write your own. In your fork this is safe and reversible:

mv CLAUDE.md CLAUDE.md.reference

Start a fresh session and let Claude draft from what it just learned answering your Step 2 questions:

inside a fresh session
/init — and use what you learned answering my questions just now. Prefer things
you verified over things you assumed, and say which is which.

Edit the result by hand, ruthlessly. Generated context files tend to be generic, and generic is worse than nothing. The valuable lines are the surprising ones — one specific rule beats three paragraphs of description.

Before you commit it, three tests, one pass each:

  1. True all the time? Anything that only matters for one part of the codebase moves out — it becomes the rule file in Step 6.
  2. Verified, not assumed? Every command in the file should be one you have actually run. /init held itself to that standard in the recording; hold yourself to the model's.
  3. Short enough to always carry? It is read at the start of every session. A 200-line CLAUDE.md is not thorough, it is skimmed. Aim well under a page.

Now the payoff: diff yours against ours.

diff CLAUDE.md CLAUDE.md.reference

Steal any line from the reference that you can verify. Notice what you wrote that we did not — that is not necessarily wrong; it may be the fresh pair of eyes. Keep your file as the live one, keep the reference beside it for the week, and from now on add to yours the cheap way: start any message with # and Claude saves the line as a memory without you opening the file.

Commit both:

git add CLAUDE.md CLAUDE.md.reference
git commit -m "My CLAUDE.md, with the original kept as reference"
git push

Part twoNow the rest of the harness

Here is the part most tutorials get wrong, so we will say it plainly: the repo you cloned already carries the harness that built it. Part two is reading that harness surface by surface, and adding the three things it deliberately lacks.

what ships in the clone · what you add in the next five steps
carrot-wall/
├── CLAUDE.md                      ← yours from Step 3; ours lives on as CLAUDE.md.reference
└── .claude/
    ├── settings.json              ← ships: formatter + migration guard
    │                                you add: permissions + two safety hooks (Step 5)
    ├── commands/                  ← ships: spec · plan · migration · ship · cleanup-worktree
    ├── agents/                    ← ships: code-reviewer (opus) · test-runner (haiku)
    ├── skills/                    ← ships: project-conventions
    ├── rules/                     ← you write: testing.md (Step 6)
    ├── hooks/                     ← you install: the two tested guards (Step 5)
    └── workflows/                 ← stays empty, on purpose

Build order matters: the guardrail hooks come first because they are the files that protect you while you experiment with everything else.

Step 4Read the harness you cloned

Ten minutes, no writing. See what is actually there:

find .claude -type f

Map each file to a surface from this morning's tour. commands/ holds /spec, /plan, /migration, /ship and /cleanup-worktree — prompts with a name. agents/ holds the opus reviewer and the haiku test-runner. skills/project-conventions/ is the one skill, and its description is worth reading twice: it names the situations that should trigger it, not a topic.

Then open settings.json. Two hooks live in it already:

  • The formatter (PostToolUse): every .ts, .html, .scss or .json file Claude edits gets prettier run on it. Boring, deterministic, gone from review comments forever.
  • The migration guard (PreToolUse): editing an existing Flyway migration is refused with exit code 2, and the message it prints to stderr goes back to Claude as the reason. That is the enforcement contract from this morning, live in the repo you are holding.

Do not take the guard on faith — bounce it:

prompt · watch it refuse
Open the oldest file under apps/api/src/main/resources/db/migration/ and add a comment
line at the top.

Watch the refusal come back with the hook's own words: existing migrations are immutable. Nothing in CLAUDE.md could guarantee that. This file just did.

Step 5Add what it lacks: safety hooks and permissions

The shipped harness formats and protects migrations, but nothing yet stops rm -rf, a force-push, or a read of .env. The teaching harness carries two stack-neutral guards for exactly this, each with a test file beside it. Bring them in:

mkdir -p .claude/{rules,hooks,workflows}
cp setup-docs/teaching-harness/.claude/hooks/* .claude/hooks/
bash .claude/hooks/block_destructive_bash.test.sh
bash .claude/hooks/block_secrets_access.test.sh

Both test scripts green? They are the half of the lesson people skip: a hook that silently does nothing is worse than no hook, which is why every one of ours ships with its test. (The teaching harness also holds an exhibit rule file, a skill and a workflow — leave those where they are; they are reading material for Steps 6 and 7.)

Now wire the guards into .claude/settings.json. It already has hooks.PreToolUse with the migration guard in it — add these two entries to that same array, do not replace it:

add inside the existing "PreToolUse": [ ... ]
{
  "matcher": "Bash",
  "hooks": [ { "type": "command",
    "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/block_destructive_bash.sh",
    "timeout": 10 } ]
},
{
  "matcher": "Read|Edit|Write",
  "hooks": [ { "type": "command",
    "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/block_secrets_access.sh",
    "timeout": 10 } ]
}

And add a permissions block at the top level of the same file — what never needs asking, and what is never allowed:

add at the top level of settings.json
"permissions": {
  "allow": [
    "Bash(./mvnw test *)",
    "Bash(npm test *)",
    "Bash(git status)",
    "Bash(git diff *)"
  ],
  "deny": [
    "Read(./.env)",
    "Read(./.env.*)",
    "Read(./**/*.pem)"
  ]
}

Settings files are strict JSON: one trailing comma or // comment and the whole file is silently ignored — which would switch off the migration guard too. So verify immediately: run /status and check the Setting sources line still lists the project file. Then bounce a guard live: ask Claude to rm -rf node_modules and read the refusal.

Why deny beats advice

The three deny lines take thirty seconds and are the highest-value lines in this guide. A CLAUDE.md rule about secrets is a wish; a deny rule is a fact. This is the advise-vs-enforce line from this morning, now in a file you own.

Step 6Write your first rule file

One folder in the tree is still empty: rules/. A rule with a paths: glob loads only when Claude touches a matching file — knowledge attached to the code it applies to, costing nothing everywhere else. Write one for the Wall's tests:

.claude/rules/testing.md
---
paths:
  - "apps/web/**/*.spec.ts"
  - "apps/api/src/test/**/*.java"
---

# Testing conventions

- Web tests run with `npm test` (vitest + jsdom). API tests run with `./mvnw test`.
- A bug fix is not done until a test reproduces the bug first.
- Never weaken or delete an existing assertion to make a suite pass —
  say what you found instead.

Replace the bullets with what you learned during the challenge — the two-session test from the exercise section below applies here too. Rules without a paths: field load at launch alongside CLAUDE.md, so a scoped rule is strictly cheaper: same knowledge, paid for only when relevant.

Step 7Run /spec, then read its rival

The wall was built through the commands you found in Step 4, and the trace is in the repo: docs/intents/ holds the spec cut into eight buildable slices, and docs/specs/ holds the spec-and-plan pair for each one. That is what a harness's paper trail looks like after a real build.

Now produce one of your own. Pick something small from feature-ideas.md and run the repo's spec command:

prompt
/spec let people react to a wall post with an emoji

It interviews you one question at a time, then writes docs/specs/<feature-name>.md. Do not skip the interview — the questions are the point. You will build from a spec like this tomorrow.

Then read the rival. The teaching harness carries a spec skill — same job, different mechanism — at setup-docs/teaching-harness/.claude/skills/spec/SKILL.md. Read it where it sits; do not install it, or it would collide with the /spec you just ran. The contrast is the lesson:

  • A command is a prompt with a name — you decide when it runs.
  • A skill is found by its description when the task matches — it decides when it is relevant, which is why its description names situations, not topics.
  • The harness skill holds zero stack facts: every noun is looked up at runtime from a memory file. Generic procedure in the skill, project facts in memory — the split you will use when you build your own on Wednesday.

Step 8Put the agents to work, then upgrade one

Both agents ship already aimed at this repo. Use the mechanical one first:

prompt
Use the test-runner agent to run both suites and report only the first meaningful failure.

The test output lands in the agent's own context window, not yours; you get back a paragraph. Open .claude/agents/test-runner.md while it runs: four lines of frontmatter — model: haiku because the work is mechanical — and one paragraph of instructions. That is the whole file.

Now the upgrade. Open the repo's code-reviewer.md next to the teaching harness's version (setup-docs/teaching-harness/.claude/agents/code-reviewer.md) and spot the differences: the harness one carries a tools allowlist, an effort level, confidence scoring and a fixed output contract. Steal the cheapest of those ideas into the repo's reviewer — add one line to its frontmatter:

.claude/agents/code-reviewer.md · add to the frontmatter
tools: Read, Grep, Glob, Bash

That is an allowlist. A reviewer that only has Read, Grep, Glob and Bash physically cannot edit your code — a different kind of safety from asking nicely. Commit the edit; the agent is now partly yours, which is how every good harness file starts.

The last surfaceWorkflows can wait — here is the pointer

The empty workflows/ folder is not an oversight. You do not hand-write these: you ask for one in words, watch it in /workflows, and if the run did what you wanted, press s — it saves into that folder and becomes a command. The exhibit spec.js in the teaching harness shows what a saved one looks like: a deterministic spine, one model per phase.

If you want the honest demo, run /deep-research on something you actually care about and read the cited report it comes back with.

VerifyProve the harness is alive

A harness you have not tested is a pile of markdown. Six checks, three minutes:

  1. /status — Setting sources lists the project settings file. If not, find the trailing comma; a broken file also switches off the migration guard.
  2. /context — your CLAUDE.md is loaded, and the project-conventions skill's description appears in the skills list.
  3. Ask for a change to a .spec.ts file — your testing rule from Step 6 should load when the file is touched.
  4. Ask it to read .env — the deny rule refuses before any hook gets a turn.
  5. Ask it to edit an existing migration — the guard bounces it with its own reason.
  6. /memory — just look. Claude has been keeping notes on you all day; you are allowed to read and prune them.

ReferenceThe six surfaces

Everything you saw on the tour this morning is one of six things. You built or installed most of them in the steps above; this is the one page to come back to when you forget where something lives.

  1. Rules — CLAUDE.md at the project root, and .claude/rules/*.md for anything bigger than a few lines. Loaded at the start of every session. A rule with a paths: glob in its frontmatter only loads when Claude touches a matching file, which is how a large project keeps its API rules out of a frontend session. Rules are context: Claude reads them and usually follows them. They do not enforce.
  2. Skills — .claude/skills/<name>/SKILL.md. At startup only the description is in context; the body loads when the work matches, or when you type /<name>. Supporting files beside SKILL.md load only if Claude chooses to read them. Write the description as a sentence about when to use it, not what it is.
  3. Agents — .claude/agents/<name>.md. A subagent runs on its own clean context window and hands back a summary, so a four-hundred-line test run costs you a paragraph. Frontmatter picks the model and can restrict tools, so a reviewer can be given Read, Grep and nothing else.
  4. Workflows — .claude/workflows/*.js. A script that orchestrates many agents: agent(), parallel(), pipeline(), phase(). The script holds the loop and every intermediate result, so your context holds only the answer. You do not write these by hand — ask for one, watch it in /workflows, and press s to save the run as /your-name.
  5. Hooks — wired in settings.json. Shell commands that run before or after a tool. A PreToolUse hook that exits with code 2 blocks the action, and whatever it prints to stderr goes back to Claude as the reason. This is the only surface that enforces.
  6. Settings — .claude/settings.json and friends. Permissions, hooks, model, output style, everything below.
The one distinction to hold on to

Rules and skills advise. Hooks enforce. If a thing must never happen — reading .env, committing to main, dropping a table — writing it in CLAUDE.md is a wish. Write it as a hook or a deny rule.

Step 9Set it up the way you like it

Ten minutes here will change how the rest of the week feels. Run /config to browse everything; the notes below are the settings worth touching on day one.

Know which file wins

Claude Code reads settings from several places and applies them in this order, highest first:

  1. Managed settings — deployed by your organisation. Always wins.
  2. claude --settings '{...}' — one session only.
  3. .claude/settings.local.json — yours, in this project. Claude Code keeps it out of your commits.
  4. .claude/settings.json — committed, so everyone who clones the repo gets it.
  5. ~/.claude/settings.json — you, in every project on this machine.

When a setting is not doing what you expect, it is almost always a higher file. Run /status and read the Setting sources line. Settings files are strict JSON — one trailing comma or // comment and the whole file is ignored.

Spend your attention where it matters

Every prompt you dismiss on autopilot is a prompt you will dismiss on autopilot when it matters. Allow the boring things explicitly, and deny the dangerous ones outright:

~/.claude/settings.json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/*.pem)"
    ]
  }
}

Those three deny lines take thirty seconds and are the highest-value thing in this guide if you work on anything regulated.

Change how Claude talks to you

An output style changes Claude's voice and format, not what it knows about your project. Five are built in: Default, Proactive (acts rather than asks), Concise (leads with the result, no narration), Explanatory (adds insights as it works) and Learning (leaves TODO(human) markers for you to fill in).

/output-style concise

Try concise today and explanatory tomorrow. Most people keep one of the two. You can write your own as a Markdown file in ~/.claude/output-styles/ — set keep-coding-instructions: true in the frontmatter if you still want Claude coding the way it normally does.

Not the same thing as CLAUDE.md

Project facts and conventions go in CLAUDE.md. Tone and format go in an output style. Putting "be concise" in CLAUDE.md spends context on every single session to say something a setting says for free.

See where you are without asking

A status line sits left of your prompt and can show your branch, model, and context use, so you stop typing /context to find out. Set it with /statusline — describe what you want and Claude writes the script — or point the statusLine setting at your own command.

Let it keep its own notes

Auto memory is on by default: as you correct Claude, it writes short notes for itself, stored per repository with a MEMORY.md index. Run /memory today and just look at what is in there. You can read it, prune it, correct it, or switch it off with the toggle in that same view. We open this properly on Day 3.

The real exerciseBuild the harness, not just the habit

The official tutorials will teach you to use the tool well, and they are worth an hour. What they cannot teach you is what your harness should contain, because that comes out of your codebase and your team's scars. These five challenges are designed to produce decisions, not output.

1 · Make it get something wrong, on purpose

Ask for a change that violates a convention in the reference CLAUDE.md — render a post message with [innerHTML], or bump upvotes with a one-line bulk Post.update(...). Does it notice? (Pick an advice-level rule: the migration one will not do, because the hook enforces it before the model gets a say.)

If it does not, you have just found your first CLAUDE.md line. The skill here is not catching the model out; it is noticing what the repo never told it.

2 · The two-session test

mv CLAUDE.md CLAUDE.md.off    # ask your question, then put it back
mv CLAUDE.md.off CLAUDE.md

Ask the same question with and without the file, and compare the two answers. If they are identical, your CLAUDE.md is not doing anything yet. That is information, not failure — most first drafts are generic, and generic is worse than nothing.

3 · Count your repeats

Work for twenty minutes and write down every correction you type more than once. Each one is a harness candidate. Then make the decision that actually matters — where does it go?

HomeChoose it when
CLAUDE.mdIt is true all the time and short enough to always carry
a commandIt is a prompt you retype, and you decide when
a skillIt should find you when the task matches, without you asking
a hookIt must hold whether or not anyone agrees

Getting the row right is the whole design skill. Most harness mistakes are a thing in the wrong row — usually everything piled into CLAUDE.md until it is two hundred lines and gets skimmed.

4 · Write the rule that would have stopped it

Pick the worst thing it did today. Write the one sentence that would have prevented it. Then ask the question that separates a sentence from a hook: would advice have been enough?

Most things are advice. The few that are not — deleting things, pushing to main, reading secrets, editing a shipped migration — are your first hooks. You installed two today; on Wednesday you write your own.

5 · Delete a line

Take one line out of your CLAUDE.md, start a fresh session, and see whether behaviour changes. A file you have never tested is a file you are guessing about. This is the same instinct as writing a test for a hook, and it is the habit that separates a harness from a pile of markdown.
